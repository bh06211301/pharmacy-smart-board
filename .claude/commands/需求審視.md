# 需求審視

在動手實作之前，審視使用者描述的需求是否有內部矛盾、與現有功能衝突、或邏輯上說不通的地方。

## 使用方式

`/需求審視 你的需求描述`

或者不帶參數，直接 `/需求審視`，我會請你描述需求後再分析。

---

## 執行步驟

**第一步：讀取現有系統脈絡**
- 讀取 `CLAUDE.md`，了解現有功能清單、資料結構、頁面職責
- 讀取 `worker.js` 頂部合約區塊，了解現有欄位與 API 定義

**第二步：逐項審視需求**

針對使用者提出的需求，檢查以下四個面向：

### 1. 內部自我矛盾
需求本身有沒有說法前後不一？
例如：「要自動排序，但也要讓我拖曳改順序」→ 兩者在觸發條件上可能衝突

### 2. 與現有功能衝突
新需求是否與已有的功能打架？
例如：「新增按鈕讓使用者手動標記完成」→ 但系統已有 checkbox toggleTodo，功能重複

### 3. 資料來源矛盾
需求中用到的資料，現在系統有沒有？從哪裡來？
例如：「顯示藥局的健保特約狀態」→ 現有藥局資料（Sheets）有沒有這欄？

### 4. 跨頁面一致性
同樣的功能在 index.html 和 field.html 的行為是否需要一致？
若不一致，有沒有充分的理由（外勤模式的限制）？

**第三步：指出模糊地帶**
找出需求中沒有說清楚的地方，可能讓我的實作方向跑偏。
例如：「讓待辦可以排序」→ 手動拖曳排序？還是自動依日期排序？兩者做法完全不同。

---

## 輸出格式

```
【需求理解】
用一兩句話複述我對這個需求的理解，讓你確認我沒有誤解。

【發現的問題】
🔴 矛盾：[說明衝突在哪裡，建議如何取捨]
🟠 衝突：[與現有功能的重疊或打架]
🟡 模糊：[需要你澄清才能繼續的地方]

【建議確認的問題】
1. ...
2. ...

確認以上問題後，輸入 /分析 [需求] 繼續進行影響範圍分析。
```

如果需求沒有任何問題，直接說「需求清晰，無矛盾」並建議接著用 `/分析` 繼續。
