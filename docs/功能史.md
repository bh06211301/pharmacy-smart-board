# 功能史

## 盤點登記（2026-08-22 完成）
- **目的**：業務外出盤點時，自動列出候選產品清單（減少手動輸入），取代原本在 AppSheet 裡逐筆手動新增太慢的問題
- **為什麼不做在 AppSheet 裡**：完整過程與放棄原因見 `apphseets製作/CLAUDE.md`「已知的重要設計細節」第 14 點——AppSheet 這個版本的 Automation 沒有原生迴圈、Add new rows 不能展開清單、Call a process 不可靠，手動展開重複 Step 的工程量與風險過高，改用真正的程式語言迴圈實作
- **前端**：`inventory.html` — 選藥局（搜尋 `/pharmacies`，或按「📍 定位最近藥局」用瀏覽器 geolocation 依 haversine 距離排序＋顯示距離，兩種模式並存不互斥）→ 帶 `session`（格式 `INV-YYYYMMDD-{8碼hex}`，前端產生）呼叫候選清單 → 逐項填數量（+/-按鈕）/備註（含快速標籤：缺貨、效期將近、包裝損壞、🚫停售(此店)）/效期 → 送出後重新載入候選清單（已送出的品項會被排除，同一 session 可分批送出多次）
- **⚠️ 盤點明細實際欄位**（跟 AppSheet 那份文件曾經記錄的「狀態」欄位對不上，那欄位實際不存在）：`明細ID,盤點編號,產品ID,產品名稱,產品數量,盤點備註,產品效期`
- **盤點主檔欄位**：`盤點編號,Visit_ID,Customer_ID,盤點日期`（`/inventory-submit` 目前 `Visit_ID` 固定寫空字串，尚未串接拜訪紀錄）
- **既有資料品質問題**：盤點明細裡有一批 2026-04-30、2026-05-07 左右、缺少 `盤點編號` 的不完整舊資料，尚未清理（缺 `盤點編號` 的列本來就不會比對進任何客戶的候選清單，不影響正確性，但如果要做「列出所有異常列」之類的清理工具要另外處理）
- **產品照片**：來源是本機 `產品資料群（找產品、型錄、業務筆記）/家中產品/產品庫/{分類}-{品名}/照片/{SKU前綴}.../L.png`（外盒正面照，優先序 L > R > C > I），縮圖後（最長邊640px、JPEG q82）上傳到 R2 bucket `pharmacy-product-photos`，經 worker.js `GET /product-photo/:sku.jpg` 服務。**69 個 SKU 中 63 個有照片，6 個目前查無本機照片資料夾（缺照片會顯示 💊 emoji 佔位，不會出現破圖）：8B、43AB、44A、46A、2C、2D**。之後若補了照片，直接把新圖丟到本機對應資料夾，重新跑縮圖腳本上傳 R2 即可（腳本沒有留在repo裡，是一次性批次工具，之後若要再跑同樣邏輯需重寫：掃描 `產品庫/*/照片/*` 子資料夾，用產品編號2 zero-pad 到2位數比對子資料夾前綴取代表照）
- **候選清單排除邏輯**（`/inventory-candidates`，2026-08-22 修正為單店範圍）：出貨明細裡買過的（比對 `店名_備份`），扣掉「這家藥局」在 `退貨明細` 裡 `退貨原因`＝`停售`（完全比對）的 SKU（**單店排除**，透過 `SHEET_RETURN_ORDER` 對照，見下），扣掉帶 `session` 參數時已經記錄在 `盤點明細` 相同 `盤點編號` 的 SKU
- **⚠️ 「停售」怎麼對到店家**（2026-08-22 確認，取代舊版「全域排除」邏輯）：
  - `退貨明細`（`SHEET_RETURN`，Sheet ID 見 worker.js 的 `SHEET_RETURN` 常數）本身**沒有店家欄位**（欄位：`退貨明細ID,退貨單號,產品ID,數量,退貨單價,小計,明細扣抵狀態,掃描入口,退貨原因,退貨備註`），但 `退貨單號` 可以對照到**另一份獨立的 Google Sheets**「退貨單」（`SHEET_RETURN_ORDER`，Sheet ID 見 worker.js 的 `SHEET_RETURN_ORDER` 常數，欄位：`退貨單號,店名,退貨日期,退貨金額,備註,退貨單實體狀態,手開單號,有實體紅單,借出日期,歸還日期`），這裡的「店名」欄位存的直接就是 Customer_ID（如 C071），不用再查客戶資料表
  - `/inventory-candidates` 用 `退貨明細.退貨單號 → 退貨單.店名` 這個 join 判斷「這筆停售退貨是哪家店的」，只在該店確實有這筆紀錄時才排除，不影響其他藥局
  - **實際資料驗證過**：每個標「停售」的 SKU 都只涉及 1~3 家店（例如 19A 只有 C071、C106 退過），不是全公司性的下架，所以單店排除才是正確行為；改之前的全域排除邏輯會誤藏其他店根本沒發生過的品項（已用 19A 對 C018 vs C071 實測驗證修正前後差異）
  - **退貨單／退貨明細的父子關係資料完整性已核對（2026-08-22）**：退貨單（主檔）47 筆、47 個不重複退貨單號；退貨明細 90 筆，剛好對應到這 47 種退貨單號；**零孤兒**（明細的退貨單號都能在主檔查到、主檔每筆都至少被一筆明細引用）；一對多分布 25:1、8:2、10:3、1:4、3:5（25+8+10+1+3=47 筆主檔，25×1+8×2+10×3+1×4+3×5=90 筆明細，剛好對上）；抽查金額也吻合（主檔「退貨金額」＝底下明細「小計」加總）。結論：這是標準乾淨的一對多父子表，跟盤點主檔/盤點明細同一套結構慣例，worker.js 的 join 可靠，不會有查無資料或金額兜不起來的風險
  - inventory.html 備註快速標籤的「🚫 停售（此店）」是另一個獨立機制：只把文字「停售」寫進 `盤點明細.盤點備註`，範圍限定那一次盤點（單店＋單次），不寫入、不影響 `退貨明細` 或 `退貨單`（這個是盤點當下手動標記，不需要真的走退貨流程）
  - 若之後真的要做到「退貨也能追蹤是哪家店」，必須先在 `退貨明細` 加一欄店家/Customer_ID（會影響現有填單流程與對帳邏輯，是需要另外決定的資料表改動，不是這次盤點功能的一部分）

## 藥局資訊總覽（2026-08-23 完成）
- **目的**：把跟單一藥局有關的所有資料（基本資料、拜訪紀錄、出貨明細、退貨紀錄、盤點歷史）整合在一個頁面查詢，取代逐一開不同 Sheets 分頁找的方式
- **為什麼不另外做一張彙整表**：討論過是否要新增一張「店家進貨/退貨總表」，決定不做——出貨明細/退貨明細/盤點明細本來就是即時可查的原始資料，另外存一張表需要額外同步機制，資料一多就會跟原始表兜不起來、反而更不可靠。改用 API 即時 join 三張表，永遠是最新資料，不用維護
- **前端**：`pharmacy-profile.html` — 選藥局（沿用 inventory.html 的搜尋／定位最近藥局模式）→ 基本資料卡（店名/地址/電話/藥師/行政區，來自既有 `/pharmacies`）→ 四個分頁籤：拜訪紀錄（既有 `/visits/:id`）、出貨明細、退貨紀錄、盤點歷史（後三項來自新 endpoint `/pharmacy-profile`）
- **後端**：`GET /pharmacy-profile?pharmacy=<Customer_ID>` 回傳 `{ orders, returns, inventory }`
  - `orders`：出貨明細依 `店名_備份` 篩選，依訂單編號解析日期（YYMMDDNN 格式）排序
  - `returns`：`退貨單`（`SHEET_RETURN_ORDER`）依 `店名` 篩選出這家店的退貨單號集合，再用 `退貨明細.退貨單號` join 進來，依退貨單分組（含退貨原因，"停售" 前端會標紅）
  - `inventory`：`盤點主檔` 依 `Customer_ID` 篩選出這家店的盤點編號集合，再用 `盤點明細.盤點編號` join 進來，依場次分組（備註含「停售」前端會標紅）
  - 三個區塊各自獨立 join，其中一個查無資料不影響其他區塊

## 拜訪App「新案開發」當場建檔（2026-10-13 完成）
- **目的**：業務在現場遇到爸爸還沒給名單的新店家時，原本的「新案開發（未建檔店家）」只是幫這次拜訪貼標籤（存到拜訪紀錄表時店名變成「NEW-店名」），不會真的寫進「新客戶資料表_AppSheet」，也沒有正式 Customer_ID。改成當場直接建檔，產生正式編號（如 C135），之後這家店就是系統裡真正的客戶
- **前端**：pharmacy-visit-app 的「新案開發（未建檔店家）」表單，新增欄位：電話、負責人姓名、職稱；地址旁加「📍 定位填地址」按鈕
  - 定位填地址：用瀏覽器 GPS，呼叫免費的 OpenStreetMap Nominatim 反向地理編碼（`https://nominatim.openstreetmap.org/reverse?lat=&lon=&format=json&zoom=18`，不需要 API key），帶出縣市/行政區/路名組成地址字串填入，門牌號碼只是起點，業務要自己核對現場門牌修正（GPS 精度不保證抓到正確門牌）
  - Nominatim 回傳的縣市用「臺」（臺北市），既有資料庫慣例用「台」（台北市），前端會先轉換回「台」再填入地址欄，跟既有資料保持一致
- **後端**：GAS `VisitAppWebhook.js` 新增 `action:'newPharmacy'` → `handleNewPharmacy_()`，跨試算表開啟 `新客戶資料表_AppSheet`（Sheet ID 見 `gas-backend/VisitAppWebhook.js` 的 `PHARMACY_SHEET_ID` 常數）寫入新客戶
  - **Customer_ID**：讀 `Customer_ID_Num` 欄（第25欄）算 MAX+1，格式 `C`+3位數補零
  - **⚠️「Key Man」欄實際存的是職稱（如「藥師」），「稱呼」欄存的才是姓名**——跟欄位名字面意思相反，但既有資料與前端顯示邏輯（`${title} ${keyMan}`）都依賴這個對應，寫入時務必保持一致，不要被欄名誤導
  - **縣市/行政區**：從地址文字開頭用正規表達式解析（`/^(.{2,3}[市縣])(.{2,3}[市區鄉鎮])/`），**沒有**照搬 AppSheet 原本的 Initial Value 公式（那個公式是靠 `EXTRACTNUMBERS([地址])` 抓地址開頭的郵遞區號數字反查，但現有地址資料都沒有打郵遞區號數字開頭，那個公式現在其實也抓不到，已確認是 AppSheet 原生新增客戶現在也會遇到的既有限制，不是這次新增功能才有的風險）。直接解析地址文字反而更可靠
  - **郵遞區號**：比照 AppSheet 實際的 Initial Value 公式邏輯（公式全文已從 `apphseets製作/appsheet/parsed_schema.json` 查到）：`ANY(SELECT(郵遞區號對照[郵遞區號], AND([縣市]=SUBSTITUTE(本列縣市,"台","臺"), [行政區]=本列行政區)))`——查 `郵遞區號對照` 分頁（跟 `新客戶資料表_AppSheet` 同一份試算表）時，縣市要先把「台」換成「臺」才能比對成功，這是 AppSheet 公式裡確認存在的轉換，不是臆測
  - 其他欄位（狀態/等級/統編/發票需求/營業時間/公休日/備註等）留空，沒有要當場收集
- **2026-10-23 加上送出前確認步驟**：pharmacy-visit-app 的「正式建檔」按鈕不再按下去就直接呼叫後端寫入，改成先跳出確認畫面列出即將寫入的欄位（含用跟後端同一套正規表達式在前端預覽出的縣市/行政區，解析不出來會標紅警告），業務員按「確認送出」才真的打 API；「返回修改」可以回去改欄位不會弄丟資料。後端 `handleNewPharmacy_` 本身沒變，只是前端多一道關卡
- **2026-10-23 加上客戶建檔紀錄（統一變更紀錄做法A）**：`handleNewPharmacy_` 寫入新客戶後，順手在同一份試算表新增/寫入「客戶建檔紀錄」分頁（欄位：時間、Customer_ID、店名、來源），來源會區分是「App現場建檔」還是「App現場建檔（原未記錄店家轉正）」（比對 `markTempPharmacyConverted_` 是否有找到對應的暫存店家）。這是目前唯一有留痕的寫入路徑——拜訪紀錄/盤點/AppSheet 原生新增客戶都還沒有對應的變更紀錄，之後如果要擴大範圍是做法B，工程量大很多，目前先只做新增客戶這塊（風險最高：GPS反解地址/AI判斷出錯就直接變成正式客戶資料）

## 未建檔店家 店名自動比對（2026-10-27 完成，不含同音比對）
- **目的**：「未建檔店家」分頁的「已轉正」欄原本只有 App 當場建檔那條路徑（`markTempPharmacyConverted_`，比對地址或店名完全相同）會自動填；透過其他管道（AppSheet 手動建檔等）轉正的客戶永遠不會回填，一直要手動對。這次補一個批次比對工具，把目前已經轉正、但「已轉正」還空白的店家抓出來
- **規則**（使用者確認，初訪店名常打不完整／打同音字／錯一個字）：
  1. 比對前先整理店名：去空白、拿掉「藥局/藥房/藥師/健保/中西/生活/藥妝」這類常見字（`simplifyPharmacyName_()`）
  2. 整理後**完全相同且只對到一家**客戶 → 自動填「已轉正」
  3. 其他可疑狀況（一個名字包含另一個／整理後只差一個字／完全相同但對到多家）→ 只寫新欄「疑似對應」讓使用者自己確認，**不**自動填「已轉正」；「疑似對應」已有值就不重寫，避免每天對同一組重複產生待確認
  5. **2026-10-27 dryRun 實測後收緊兩條規則**（原始版太鬆，「森康」整理後只剩2字，靠「差1字」對到8家不相干的店——群康/安康/易康/森采/德康/唯康/保康/永康）：
     - 「差1字」只在**兩邊**整理後店名都 ≥ 3 個字時才比對，2字以下的短店名只用「完全相同」跟「包含關係」判斷
     - 同一家未建檔店家若疑似對應**超過2家**（3家以上），視為太模糊，直接當「對不到」，不寫「疑似對應」（避免塞一堆雜訊讓人工確認失去意義）
  4. **同音比對目前沒做**：跟使用者討論過 Apps Script 沒有 npm、不該直接掛完整拼音字典（上萬字太肥），建議改成只收實際出現在店名裡的字（估計幾百字內）做一份小型「聲母+韻母」對照表，比照 LINE 速記同音錯字表的養成方式；要等實際評估字集大小後再動工
- **實作**：`gas-backend/VisitAppWebhook.js`
  - `TEMP_COLS` 新增 `疑似對應`；**部署前必須先手動執行一次** `addSuspectedMatchColumnToTempSheet()` 幫既有「未建檔店家」分頁表頭補上這欄（只在表頭還沒這欄時才新增，不動既有資料）
  - `simplifyPharmacyName_()` / `isOneCharDiff_()`：規則 1、3 的比對邏輯
  - `matchTempPharmacyNames_(dryRun)`：核心比對，`dryRun=true` 完全不寫入，只把每一家未轉正店家的比對結果（`自動填`／`問我`／`對不到`）用 `Logger.log` 印出來，供使用者檢查規則準不準
  - 入口函式：`dryRunTempPharmacyNameMatch()`（先跑這個看結果）、`runTempPharmacyNameMatch()`（確認沒問題後真的寫入）——都要在 Apps Script 編輯器手動點「執行」，`clasp run` 在這個專案跑不起來（同 new-pharmacy-screening 的已知限制）
  - 跟即時比對 `markTempPharmacyConverted_()`（當場建檔用）是兩套獨立邏輯，互不影響：即時比對只抓地址/店名完全相同，這個批次比對專門補即時比對抓不到的其他轉正管道
- **Phase 2 想法**（已記在 `docs/SPEC.md` 第11節）：pharmacy-visit-app 輸入新店名時跳出建議清單（篩選器名單＋客戶表）讓業務直接點選，從源頭減少打錯店名，還沒排進哪個階段

## 死客戶／爸爸客戶 改欄位化（2026-10-24 完成）
- **背景**：原本死客戶是 `/recommend-today` 裡算出來的猜測（`totalAmount>0 && daysSince>180 && !visitCount`），跟另一套獨立的「客戶狀態」GAS 代理（`GAS_URL`，該 GAS 專案原始碼從未存在本機，只能用現有部署）並存；爸爸客戶則是 Cloudflare KV（`dad:pharmacies`）。使用者直接在 `新客戶資料表_AppSheet` 主表加了兩個真欄位：**Z 欄「停用」**（任何非空文字＝死客戶，空白＝正常；值是原因文字如「業績不佳」「歇業」）、**AA 欄「負責人」**（Enum「我」／「老爸」，2026-10-13 在 AppSheet 編輯器自建，空白視為「我」），兩欄都已經手動填好全部既有客戶的資料，比舊的 KV 預設清單（只有 12 家、含一筆已過期的 C125）更新更準，所以直接切過去，不做新舊並存
- **worker.js**：

## LINE 速記解析（2026-10-23 完成，第一版）
- **目的**：使用者平常在 LINE 上用極簡速記打拜訪時的訂單筆記（店名+產品暱稱+數量黏在一起，常有語音輸入造成的同音錯字），探索能否自動解析成結構化資料。先拿真實歷史訊息跟使用者逐一核對過可行性（詳細驗證過程、錯字對照表見使用者端記憶 `line-order-shorthand-parsing`），這版把驗證過的邏輯做成一個獨立小工具
- **前端**：`line-notes.html` — 單頁，貼上/打字速記文字 → 按「整理成訂單草稿」→ 顯示解析結果（依推測的拜訪分組，每組顯示店家、品項、信心等級徽章；查無對應的品項/店家會明確標紅，不會亂猜）。**純顯示，不會寫入任何資料表、不會送出到任何地方**——跟「AI當場建檔」同一個原則：AI 判斷不可靠的環節，先讓人看過再決定要不要手動處理
- **後端**：`POST /parse-line-notes`（`handleParseLineNotes`），即時抓真實的 `SHEET_PRODUCT`／`SHEET_PHARMACY` 清單餵給 AI 當比對依據（不是憑空猜產品/店名），prompt 裡帶驗證過的錯字對照表當提示，並明確要求「查不到就老實標 null，不要掰一個相近的」
  - **2026-10-24 改走 OpenRouter，不再直接打 Gemini**：Cloudflare Workers 直接打 Gemini API 會遇到「User location is not supported」地區限制（Cloudflare 出口 IP 不固定，剛好分配到 Google 不支援的地區就會被拒絕，跟帳號/金鑰/模型都無關），照抄 visit-worker（2026-10-07）已驗證穩定的做法：8 個免費備援模型清單（`nvidia/nemotron-3.5-super-vl:free` 等，見 worker.js `handleParseLineNotes` 內 `models` 陣列）＋ JSON 驗證重試（拿到的回應不是有效 JSON 就換下一個模型，不是「有內容」就算成功）＋ 雙重逾時保險（AbortController 10 秒 + `Promise.race` 逾時 Promise）＋整條備援清單合計最多 25 秒，時間到就放棄不再多試。OpenRouter 免費模型會持續變動/下架，之後若大量失敗，用 OpenRouter 的 `/api/v1/models`（公開、不需金鑰）重新查當下還在架上的模型即可
  - **時間分組規則**（使用者提出、拿真實資料驗證過）：同一天內訊息間隔在15分鐘內視為同一次拜訪（即使沒重複打店名），間隔超過1小時視為換店
  - 排班提醒、人名評語、純店名列表、純圖片訊息這類非訂單內容，會被篩進 `skippedLines` 回傳，不會污染品項解析
  - 只回傳 JSON 結構給前端顯示，**沒有**接回 GAS 寫入拜訪紀錄表或訂單主檔——這一步要不要接、接了之後資料要怎麼進正式系統，還沒做，是故意先停在「看得到整理結果」這一步
