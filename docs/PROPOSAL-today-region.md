# 方案：A1「今天可以跑的區」

> 只寫方案，沒有動手實作。對應使用者 2026-11-02 的工作項目 7。

## 你的判斷方式（先確認我有理解對）

> 先看新店分布在哪幾區，再看哪一區剛好有貨要送，選一區當天跑完，其他區改天。能去就都去，
> 主要看距離和時間。

所以這個畫面的角色是「幫你快速看完『每區概況』，由你自己決定選哪一區」，系統**不計算最佳路線、
不自動選區、不決定日期**——這點跟現有 5.5（A1 待追蹤排進某天）「系統不自動決定改到哪一天」的
原則一致，這份方案照這個原則設計。

---

## 1. 區域怎麼分群

**沿用現有的「市→區」分組（`planner-shared.js` 的 `groupStoresByRegion()`，這次項目 2 剛把市
排序改成依家數），不另外發明一套分群邏輯**。原因：

- 使用者已經很熟悉這套分法（A2 店家規則左側清單同一套）。
- 店家資料本身的 `city`/`district` 欄位已經很完整（A2 查過 136 家正式客戶、新店的篩選分頁也有
  同樣的欄位），不需要用座標做地理聚類分析這種更複雜的作法。
- 「區」在台灣的實際意義（鶯歌區、汐止區…）本來就是業務熟悉的拜訪單位，比演算法分群更直覺。

畫面上以「區」為單位列卡片（不是先市後區兩層——這裡目的是快速掃過去選一區，不需要 A2 那種
收合瀏覽結構），同一區塞不下的店用「看全部」展開，比照 A1 現有「建議加入」清單的作法。

## 2. 每區要顯示的 4 個數字，資料怎麼來

| 數字 | 資料來源 | 算法 |
|---|---|---|
| 新店家數與最高倍數 | 篩選分頁（`new-pharmacy-screening`），跟 A10 `/api/funnel/overview` 同一份資料 | 依 `district` 分組算家數；倍數算法沿用現有 `handlePlannerPlan` 新店倍數公式（這次項目 1 已經補了地址，這裡直接複用同一批資料，不用多打一次 API） |
| 該區業務親送的貨 | `handlePlannerPlan` 既有的「送貨」錨點邏輯（`worker.js:2236`，來源標 `送貨`，條件是訂單「業務親送」） | 依這些店的 `district` 分組算家數 |
| 該區該拜訪的客戶數 | `/api/plan` 的 `recommended`，`type==='customer'` 且 `ratio>=1`（跟現有「正式客戶」區塊「該去了」判斷同一條規則） | 依 `district` 分組算家數 |
| 從汐止的大約車程 | 見下一節 | — |

這四個數字跟 A1 現有①②欄位（錨點、順路推薦）讀的是**同一份 `/api/plan` 資料**，不用再另外
打一次後端——只是把現有的 `recommended`/送貨錨點資料換一種分組方式（依區，不是依類型）呈現。

## 3. 車程怎麼估：要不要用 Google Maps、成本多少

### 現況

專案裡**已經有一組 Google Maps API key**（`GMAPS_KEY`，寫死在 `index.html`/`planner.html`
前端，目前只用在 Geocoding API 跟 Maps JavaScript API）。這把 key 能不能直接拿來打 Distance
Matrix／Routes API，要看 Google Cloud Console 裡這把 key 有沒有限制 API 清單——**需要你去
Console 確認/開通**，我這邊看不到那個金鑰背後的 GCP 專案設定。

### 建議作法：用 Routes API（Google Maps 新一代距離／時間 API），但做成「算一次、存起來、很少重算」

不建議「每次打開 A1 就即時算全部店家車程」，原因：
1. 浪費——店家地址幾乎不會變，車程也不會變，沒必要每次都重算。
2. 慢——幾十到上百家店同時算，會拖慢頁面。

改成：**Worker 排程（Cloudflare Cron Trigger，目前這個 Worker 還沒用過這個功能，需要在
`wrangler.toml` 加一段 `[triggers] crons = [...]`）每週跑一次，把「汐止 → 每家店」的車程結果
存進既有的 `TODOS_KV`（這個 Worker 已經在用的 KV，不用新建資源）**，A1 載入時直接讀 KV 裡
存好的數字，不即時呼叫 Google。新店/新客戶出現時，下一次週排程會自動補上，不用手動觸發。

### 成本估算

Google Routes API（`Compute Route Matrix`）定價：每月前 10,000 次請求免費，之後依量遞減（Basic
約 $5/千次）[2]。這個工具只有一個固定起點（汐止）、店家數大約 150～200 家（136 正式客戶＋十幾
家開發中新店），**一次完整重算只需要約 150～200 個「元素」**，每週跑一次、每月約跑 4～5 次，
一個月也才 1,000 個元素左右，**完全落在免費額度內，實際上不會產生費用**。舊版 Distance Matrix
API 免費額度是每月 5,000～10,000 個元素（視 SKU）[1][2]，也一樣夠用——兩者都可以，Routes API
是 Google 現在主推的新版，建議用這個。

### 退路：不想處理 Google Maps 設定/帳單的話

可以先用直線距離（haversine，跟 A1 現有「錨點 2 公里內」篩選用的同一個函式）換算成「大概車程」
（例如直線距離 × 1.4 的經驗係數再除以平均市區車速估算分鐘數）。**零成本、零額外設定**，缺點是
市區有橋樑/單行道/交流道的地方會估得不準（汐止到林口這種有特殊地形的路線誤差可能較大）。可以
先上線這個版本，之後要不要換成真實車程再說——不影響其他部分的設計。

## 4. 畫面長怎樣

比照現有 A1 的「步驟」卡片風格（每個區一張卡），放在現有①②欄前面，當作「第 0 步」或是用一個
新的分頁/分段呈現（待你選，見下方問題）：

```
┌─────────────────────────────────────────┐
│ 今天可以跑的區                              │
├─────────────────────────────────────────┤
│ 板橋區          [選這區]                    │
│ 新店 3 家（最高倍數 5.43）                   │
│ 送貨 2 家 ・ 客戶該去 4 家                   │
│ 車程約 28 分鐘（從汐止）                     │
├─────────────────────────────────────────┤
│ 汐止區          [選這區]                    │
│ 新店 1 家（最高倍數 1.2）                    │
│ 送貨 0 家 ・ 客戶該去 2 家                   │
│ 車程約 5 分鐘（從汐止）                      │
└─────────────────────────────────────────┘
```

按「選這區」：把這區的新店卡片＋送貨錨點**預先勾選/加入**到現有①②欄（等同你自己一個一個點選
的效果，不會自動變成「今天的路線」，計算路線、决定去哪幾家、哪天去，還是你自己在①②③操作）。
沒有新店、沒有送貨的區不特別隱藏（可能你還是想看客戶該去家數決定要不要去），但家數全是 0 的區
可以預設收合或排到最後（細節可以等做的時候再調）。

## 5. 待你確認的問題

1. 這個區塊放在 A1 現有頁面的哪裡？（a）現有①②③左邊再加一欄（可能太擠，現在已經是三欄版面）
   （b）放在①的上方，當作選完區才看①②③（c）獨立一個分頁（類似現在規劃中的 A5/A6）。
2. 車程要不要真的串 Google Routes API？還是先上線 haversine 估算版本（零成本零設定，之後要
   换成真實車程再加）？
3. 如果採用 Google Routes API，需要你去 GCP Console 確認/開通現有 `GMAPS_KEY` 的 API 權限，
   或是申請一把新的、限制更嚴格的 key 專門給伺服器端（Worker secret）用——这把 key 不會暴露在
   前端，比現有前端 key 更安全，但需要多一道設定。
