# 方案：A1、A8「先顯示再背景存檔」

> 只寫方案，沒有動手實作。對應使用者 2026-11-02 的工作項目 10。

## 現況

`planner.html`／`store-drawer.js` 現在所有會寫入資料的操作都走同一個 `withBusy(btn, label, fn)`
共用函式（2026-10-28 補的，見兩份檔案裡的註解）：按下按鈕立刻 `disabled`＋改文字（例如「加入
中…」），等整個 `fn()`（本地狀態更新＋重繪＋`await` 呼叫後端）跑完才解除忙碌狀態。這是為了解決
「連點好幾次、以為沒反應」的真實踩坑（A8 新增待追蹤連點 5 次建了 5 筆重複資料），所以現在**故意
設計成讓使用者感覺到「正在處理」**。

細看 `planner.html` 的 `addAnchor()`/`removeAnchor()`，其實已經有一半的「先顯示」效果：本地的
`anchors` 陣列先 `push`/`splice`、`renderAnchors()` 立刻重繪，**之後才** `await savePlanState()`
送到後端。但因為外層包著 `withBusy`，使用者還是要等整個存檔完成，按鈕才會恢復——視覺上畫面雖然
先動了，但「操作有沒有完成」這件事還是跟存檔綁在一起，沒有真正做到「先顯示完全不用等」。

**而且現在失敗處理有缺口**：`withBusy` 失敗時只是 `alert('失敗：' + e.message)`，`addAnchor`
本地已經 `push` 進陣列、畫面也已經顯示出來的那個錨點**不會被移除**——使用者會看到「畫面上有，但
其實沒存到後端」的資料，重新整理頁面後才會發現錨點不見了，期間完全沒有提示說「這其實沒存成功」。

## 想做的效果

> 先顯示再背景存檔

拆成兩件事，分開處理：

### 1. 操作「感覺起來」要是立即完成的，不要讓使用者等存檔

按下按鈕 → 本地狀態＋畫面立刻更新（已經有的部分）→ 按鈕立刻恢復正常（不再整個卡在「加入中…」
直到存檔完成）→ 背景送出存檔 request，不擋住後續操作。

### 2. 存檔如果失敗，要能夠復原＋明確告知，不能讓畫面說謊

背景存檔失敗時：
- 把本地狀態改回操作前的樣子（`addAnchor` 失敗要把剛加的錨點移除、`removeAnchor` 失敗要把
  移除的錨點加回來），重繪。
- 用比 `alert()` 更不突兀但一定看得到的方式通知（例如現有的 `toast()`，但要能停留久一點、
  用紅色跟成功的綠色 toast 區分開，不能跟現有「已加入」那種 2 秒就消失的 toast 長一樣——失敗
  訊息如果也是 2 秒閃過，使用者很可能根本沒看到）。

## 範圍：哪些操作要做，哪些先不動

這個模式不是「整個專案全部重寫」，建議分批、照風險排序：

| 優先度 | 操作 | 理由 |
|---|---|---|
| 高 | A1 錨點（加入/移除「今天一定要去」） | 使用者操作頻率最高，本來就已經有一半的本地優先更新邏輯，改起來风险最低 |
| 高 | A8「加入今天」 | 同上，使用模式很像 |
| 中 | A8 新增待追蹤／新增規則 | 目前沒有本地優先更新（整個表單送出後才重繪），要多做「先在清單裡插入一筆『處理中』的暫時項目」這一步，工程量比上面兩項大 |
| 低 | A10 記結果（推進/維持/放棄/確認已建檔） | **這項建議不要做成樂觀更新**。理由：A10 的「記結果」牽涉兩個外部系統（gas-backend 階段歷程＋new-pharmacy-screening 篩選分頁）協調寫入，本來就有「核對後決定要不要回滾」這種只有送出後才能判斷成功與否的邏輯（見 `docs/SPEC.md` 5.9），不適合先讓畫面顯示「已經轉正式」再回滾——萬一真的要回滾，使用者會看到階段先變了又變回去，比等待更讓人困惑。這項維持現在「送出→等結果→才更新畫面」的作法。 |

## 技術上要注意的細節

1. **同一個項目同時有兩個操作在背景跑的情況**：例如使用者很快點了「加入」又點「移除」同一家店，
   兩個背景 request 的回應順序不保證跟發送順序一樣。需要幫每個項目加一個簡單的「版本號」或
   「最後一次操作的 requestId」，背景存檔回來時先檢查這還是不是「最新的那次操作」，不是就不要
   套用這個結果（避免舊的回應把新的畫面狀態蓋回去）。這個概念專案裡已經有雛形——`PlannerActions.js`
   的 `withRequestDedup_()` 是後端防止「同一個請求重複寫兩次」，這裡要做的是前端版本，概念類似但
   目的不同（這裡是「只套用最新結果」，不是「防止重複寫入」），需要另外寫，不是直接複用那支。
2. **頁面關閉/切頁時背景存檔還沒完成**：目前 `savePlanState()` 是 `fetch` 呼叫，使用者如果存檔
   送出後 1 秒內就切頁離開，大部分瀏覽器會讓這個請求繼續送完（不會立刻砍斷），但沒有辦法保證
   100%。可以考慮用 `navigator.sendBeacon`（瀏覽器專門為這種「頁面離開時还要送最後一筆資料」設計
   的 API）取代一般 `fetch`，但 `sendBeacon` 只支援 `POST`、拿不到回應內容，如果要在失敗時做
   回滾通知，`sendBeacon` 用不上——這是「要不要做離開時的保證送達」跟「失敗要不要能夠回滾通知」
   兩個目標互相衝突的地方，需要你決定哪個優先。

## 待你確認的問題

1. 範圍先做「高優先」兩項（A1 錨點、A8 加入今天）就好，還是要連「中優先」（A8 新增待追蹤/規則）
   一起做？
2. 失敗通知要做成什麼樣子——現有 `toast()` 改款（停留久一點、紅色），還是要更明顯的方式（例如
   畫面上固定一塊「有 N 個操作沒有存檔成功，點這裡查看」）？
3. 「頁面關閉時背景存檔还沒完成」這個邊界情況，要不要特別處理（上面提到的 `sendBeacon` 取捨），
   還是先不管、接受極少數情況下可能漏存（目前現有寫法本來就有同樣的風險，不是這次才新增的）？
