1. **拜訪目的→拜訪類型自動預選的優先序**：規格（外勤模式_規格.md:53）寫「送貨→送貨、
   對帳請款→收款、新店開發→新案開發、其他→巡視」，但拜訪目的允許複選（例如同時選「送貨」
   跟「對帳請款」），這種情況下「拜訪類型」單選要自動選哪一個？這份計畫先假設優先序是
   **新案開發 > 對帳請款(收款) > 送貨 > 其他(巡視)**（新店開發最明確、收款次之，理由：收款
   是金流事件，比單純送貨更該被記錄成主類型），但沒有依據可以確定這就是你要的順序，需要你
   確認或改。
2. **「下次要記得」要不要直接等同 addFollowup**：階段1計畫下面把「下次要記得」設計成直接呼叫
   既有的 `addFollowup`（期限類型「下次經過」），跟 A5 本週頁同一套待追蹤機制共用；但
   `外勤模式_規格.md` 原文沒有明講這點，是這份計畫的推論。如果你想要「下次要記得」是獨立於
   待追蹤系統之外的欄位（只存在拜訪紀錄裡，不建待追蹤列），要先說，會影響 3/3b 畫面存檔時
   要打幾支 API。
3. **老爸提醒的「下次要記得」規則要不要保留 field.html 的關鍵字判斷**：
   `外勤模式_規格.md:57` 寫「舊 field.html 的規則保留：內容含送貨／帳單等字眼且是老爸的店→
   建立『還帳單給爸爸』提醒」，這是關鍵字比對「拜訪內容」文字；階段1計畫目前照抄沿用，但
   沒有確認過 field.html 實際的關鍵字清單是否還適用（可能需要微調字眼）。
4. **1a／4a 加站時「插在哪裡」的到達時間試算，要不要在階段1就接真實 Routes API**：規格要求

## 三、階段1剩餘步驟（真正符合規格定義的「唯讀畫面」）

### 步驟 1：首頁串接真實資料（取代假資料）
- 改 `field-v2.html`：進頁時呼叫 `GET /api/today-plan?date=今天`（讀今日行程列表）＋
  `GET /api/plan?date=今天`（讀分級/倍數/警示標籤，跟首頁「下一站」卡片的「大咖」「該去了」
  這類標籤對齊）。
- 兩支回應要合併成畫面需要的單一資料結構：用店家代號（`storeId`）比對兩邊，今日行程的
  `todayPlanRowToObj_` 形狀跟 `/api/plan` 的 `recommended` 清單形狀不一樣，需要寫一個
  `mergeTodayPlanWithPlanDetail_()` 之類的前端函式（純前端，不改 Worker）。
- 「預估收工」用今日行程各列的「預計到達」＋「停留分鐘」算，照抄 `approxFinishTimeFromRows_`
  的邏輯（worker.js 已有同款算法，前端再實作一份，不是呼叫 Worker——跟其他頁面「故意複製
  不共用」的既有慣例一致）。
- 驗證方式：wrangler dev 起 Worker，`field-v2.html` 用瀏覽器打開連到 `http://127.0.0.1:8787`，
  手動排一天的今日行程（這段本身是讀取，呼叫既有的 `GET /api/today-plan`，不會寫入），確認
  畫面資料跟試算表一致。**不送任何 POST。**

### 步驟 2：到店畫面串接真實資料
- 呼叫 `GET /api/store?id=店代號`（規格 2 到店畫面要的分級/警示/天數/倍數/上次拜訪2筆/
  待追蹤與規則，worker.js 已有 `handleStoreDetail` 對應這支，A8 藥局檔案抽屜已經在用同一支，
  直接沿用不用新開端點）。
- 「AI 拜訪前簡報」沿用藥局檔案既有的話術產生邏輯（`handleGenerateScript`），是 POST 但
  不寫入任何試算表/GAS（只呼叫 Gemini 產生文字），驗證時要特別註明這支雖然是 POST 但不算
  「會寫入」的請求——如果要在正式環境驗證，仍然要先問過你，不能自己判斷「這支 POST 應該
  沒問題」就直接送。
- 驗證方式：同步驟1，wrangler dev 本機。

### 步驟 3：收工畫面串接真實資料
- 統計數字（完成/跳過/對帳家數/新增待追蹤）從當天的今日行程列表（已經在步驟1抓過）直接
  算，不用額外呼叫新端點。
- 老爸的事清單：從今日行程裡「來源」或拜訪類型判斷哪些店負責人是老爸，沿用 `/api/plan`
  回應裡店家的 `owner` 欄位（worker.js 的 `allPharmacies` 已經有這個欄位，`/api/plan` 的
  `recommended` 清單目前沒有直接帶出來，需要確認要不要新增這個欄位到回應——這點等步驟1
  實際串接時再確認是否要改 Worker，要改之前照規矩先列出來給你同意）。

### 步驟 4：390px 寬驗證＋ Playwright console 檢查
- 依 CLAUDE.md「開發規則」：前端部署前用 Playwright 開正式頁面確認 console 無 exception。
  階段1範圍只到本機 `wrangler dev`，還不到「部署前」，但一樣會跑一次 Playwright 檢查。

**以上步驟 1～4 都只讀資料（GET為主，AI簡報那支POST不寫入），全程 `wrangler dev`，
不會對正式環境送出任何請求，更不會送出任何零寫入以外的探測——目前還沒開始動手，
是下一輪工作要做的事。**

## 五、部署步驟（還沒執行，列給你參考，部署要等你在場）

今晚所有改動都只到「本機 commit」，完全沒有 deploy、沒有 clasp push/deploy、沒有碰過任何
GAS deployment、也沒有 push 到 GitHub main（詳見 `docs/外勤模式_今日進度.md` 的分支狀態）。
之後要部署時，建議順序：

1. **gas-backend**：`clasp push` 推上 `PlannerActions.js`／`VisitAppWebhook.js` 的改動
   （`updateTodayPlanRow` action）→ 在 Apps Script 編輯器手動執行一次 `testUpdateTodayPlanRow()`
   確認全部斷言通過（需要先執行過 `addTodayPlanTestSheet()`，如果還沒建過 `今日行程_TEST`
   分頁）→ 確認通過後 `clasp deploy -i <GAS_VISIT_URL的deploymentId>`（沿用既有部署，不新建）。
2. **new-pharmacy-screening**：`clasp push` 推上 `Code.gs` 的「試賣中」移除改動 → 在編輯器
   手動執行 `testFunnelStageAction()` 確認全部斷言通過 → `clasp deploy -i <既有deploymentId>`。
   **這支要先部署**，因為 worker.js 的 `handleFunnelResult`／`handleFunnelOverview` 邊界
   （idx>1 advance、idx>2 drop/confirm）假設篩選分頁已經不會再出現「試賣中」這個字串，
   如果 Worker 先部署、GAS 還沒部署，舊資料裡如果還有「試賣中」的列會跟新的 idx 邊界邏輯
   對不上（例如舊「試賣中」列的 idx 用新 STAGES 陣列算會變成 -1，advance/drop/confirm
   全部會被新邏輯誤判成「目前階段不允許」）。
3. **pharmacy-smart-board**（`still-meadow-0efd`）：先 `wrangler dev` 本機驗證一輪（含
   `/api/today-plan/row` 對 `今日行程_TEST` 的真寫入測試，`/api/funnel/overview` 確認
   試賣中已消失、`/todos` 確認 404）→ **刪除 `GAS_URL` 這個 wrangler secret**（`wrangler
   secret delete GAS_URL`，不是改值，因為這支已經完全不用了）→ `wrangler deploy` → 比照
   昨晚的規則：deploy 後至少等 5 分鐘＋`wrangler tail`確認版本，才能用缺欄位探測驗證正式
   環境，不能送任何預期會寫入的請求。
4. 三個 repo 的 `feature/field-v2-stage1` 分支，確認部署驗證都通過後才個別 merge 回 main
   並 push（目前只有 gas-backend／new-pharmacy-screening 已 push 分支到 GitHub 備份，
   pharmacy-smart-board 的分支還沒 push，原因見 `docs/外勤模式_今日進度.md`）。
