## 0. 給 Claude Code 的工作原則

1. 每個階段開始前，先列出「要新增或修改的檔案」與「Sheet 要新增的欄位或分頁」，等我確認後再動手。
2. 只在 `planner-v2` 分支工作。GitHub Pages 讀 main，現有的 `index.html`、`tasks-page.html`、`recommend.html` 在新版穩定前保持可用，不要改動。
3. 新頁面另開檔案（例如 `planner.html`），不要覆蓋舊頁。
4. AppSheet 正在使用的表（新客戶資料表、拜訪紀錄、訂單主檔），**只能新增欄位，不能改欄名、刪欄或改順序**。要改結構時先問我。
5. 交付完整可貼上的檔案，不要只給片段 diff。
6. 規則或參數（間隔天數、加分、半徑）一律集中在一個設定檔，不要寫死在程式裡。

## 1. 要解決的問題

現在系統裡三個功能是分開的：

| 現有功能 | 位置 | 問題 |
|---|---|---|
| 月曆排程 | `index.html` 月曆 | 要手動把店排進某天，實際上沒在用 |
| AI 評分推薦 | `recommend.html` | 只排名，不知道今天會去哪一區，推薦不具體 |
| 路線規劃 | `tasks-page.html` | 選好店才算路線；油費估算沒有實際用處 |

實際的使用情境：

- **每天早餐時在電腦上規劃**。老爸會說今天要送哪幾家，這些店就是當天的「錨點」，其他店是繞著錨點補進去的。
- 起點和終點每天固定：汐止辦公室出發（約 13:30），收工回內湖（目標 17:30 前）。
- 每天約 3 家陌生開發，來源是新開藥局篩選器裡標「要去」的店。
- 藥師的特殊規則（例如週一不能去）現在只記在腦中，容易忘記。
- 週五自動排的下週草稿目前沒有發揮作用，**不以週計畫為核心**。
- 評分最看重兩件事：**多久沒去**、**有沒有待追蹤事項**。叫貨金額只在同分時用來決定先後。
- **拿掉油費估算**，改成顯示預估收工時間。

## 2. 核心流程

```
早餐：輸入今天一定要去的店（錨點）
  → 系統在錨點附近推薦順路可補的店（依分數排序，標出推薦理由與規則衝突）
  → 勾選加入，違反「擋住」類規則時跳出選項
  → 自動排順序，顯示預估收工時間
  → 確定，送到手機外勤模式
```

月曆不再負責每天排店，只放「指定日期的事」（約好的、請款日、有期限的待追蹤）和「每天跑哪一區」。

**2026-10-25 轉換結果（已完成，不用再查一次）**：查過全部 134 家客戶——
- 「營業時間」126 家有值，但都是 Google 地圖自動帶入的制式週間時段，不是人工填的排程規則，**沒有轉**；這份資料改在第 2 階段排路線時讀取使用（見 5.2）。
- 「公休日」只有 5 家有值，且全是「正常營業」「未提供」這種空泛文字，**沒有一筆是具體規則，沒有轉**。
- 「備註」只有 C014 來福藥局一筆真的是規則（「隔月5號請款」，真正意思是：寄賣通常約 7 個月才整理請款，來福是例外，下個月 5 號就要收）。已轉成店家規則：`店家代號=C014、規則類型=請款規則、每月日期=5-5、說明=「隔月5號請款（不走寄賣7個月）」、排程處理=提醒、來源=自己`。

**GPS（緯度/經度）每日補空白（2026-10-25 完成）**：獨立小工具 `new-customer-gps-tool/`（Script ID `1hJZ0RzGDGHj0Noe0fntuCYAkH-FDVkckA_rONuQ7vg6XmQMX1CKQ4Lbc`，Container-bound 在這份試算表上），跟 SmartRoute 本身無關，但第 3 階段 A9/A1 的「2 公里錨點半徑篩選」（見 4.3）要靠 W/X 兩欄才能算距離，所以這裡記一筆：
- 用 Apps Script 內建 `Maps.newGeocoder()` 查座標（不需要 API key），地址查詢前會整理過（去郵遞區號/台灣臺灣、臺→台、全形→半形、去「XX里」），整理後地址只用來查詢、不回寫 H 欄。
- I 欄寫「緯度, 經度」（逗號後留空格，固定 7 位小數），同時分開寫入 W（緯度）、X（經度）兩欄。
- 兩個可安裝觸發器：`handleEditTrigger`（編輯 B 店名或 H 地址時即時查）、`dailyFillBlanks`（每天 06:00 掃全表補空白）。**一律只補空白，已有座標的列不動**，不會覆蓋手動填過的資料。
- Places API（營業時間/公休日/照片）為選配，金鑰存在指令碼屬性 `PLACES_API_KEY`，沒設定就跳過，不影響座標查詢。

## 4. 評分

### 4.1 建議回訪間隔（新店開發，未改版）

| 階段 | 建議間隔 | 起算日 |
|---|---|---|
| 發現 | 7 天內初訪 | 進入階段日期 |
| 初訪後 | 10 天內二訪 | 進入階段日期 |
| 二訪後 | 14 天內談試賣 | 進入階段日期 |
| 試賣中 | 14 天回訪看銷況 | 進入階段日期 |

正式客戶的建議間隔改由分級決定，見 4.5——不再是固定 21 天。

### 4.2 公式（新店開發專用，未改版）

```
倍數 r = 距進入階段天數 / 該階段建議間隔

間隔分 = min(r, 2.0) × 50                     → 0～100

待追蹤分 = 各筆未完成待追蹤加總，上限 40
  指定日期前，剩 3 天內（含逾期）   +30
  指定日期前，剩 4～7 天            +20
  指定日期前，剩 8 天以上           +10
  下次經過                         +10

總分 = round(間隔分 + 待追蹤分)
```

**只適用於「藥局每日異動追蹤」篩選分頁裡還在開發階段的新店**（`type: 'new-store'`）。正式客戶改用 4.5 的新公式，兩套完全獨立，互不影響。

### 4.3 推薦清單的篩選

1. 排除規則見 4.5（死客戶／老爸／新竹縣市／狀態=不拜訪）。
2. 只列出距離任一錨點 **2 公里內** 的店（半徑可在畫面上切換，預設 2 公里）——**還沒實作，等 A1 錨點 UI 做出來**。
3. 規劃日違反「擋住」規則的店：**照樣列出但變灰**，標示規則內容。
4. 每家顯示推薦理由，例如「大咖　23 / 21 天 = 1.1 倍　月均 $3,720」。

### 4.5 正式客戶分級與排序（2026-10-27 第二版）

**為什麼改**：舊公式倍數封頂在 2.0，一堆超期很久的店全部卡在同一個分數，只能靠「近12個月叫貨金額」決勝——但叫貨金額本身沒有倍數調整過，新店（月均看起來很高但可能只是蜜月期）會不公平地排到老客戶前面。改版把「有沒有在成長／停滯」跟「規模」分開看。第一版（倍數只看拜訪日、從未拜訪排最前）實測後發現拜訪紀錄覆蓋率太低，14/15 名都卡在「從未拜訪」組，改成第二版：倍數改回看「最後接觸日」（拜訪或叫貨取較近），拿掉「從未拜訪排最前」。

**排除**（統一叫「不拜訪」，取消「其他通路」這個名字；都在分母外，推薦清單跟客戶總覽頁分級統計都不列入，但要能在 A1 手動加成「送貨」錨點——**這點等 A1 做錨點 UI 時處理，現在的 `/api/plan` 還沒有錨點概念**）：
- 新客戶資料表 Z 欄「停用」有值 → 死客戶，無條件排除，不算進下面三類。
- AA 欄「負責人」＝老爸 → 系統對老爸那邊的叫貨大多沒有紀錄，混進分析會灌水。
- F 欄「縣市」＝新竹縣或新竹市（清單在 `planner-config.js` 的 `excludedCities`，自動判斷）。**C130 艾美藥局縣市欄本來就是新竹縣，這條規則已經會抓到它，沒有另開例外清單。**

**分級門檻**（只用排除後剩下的客戶群算；門檻與間隔都在 `planner-config.js` 的 `tierThresholds`/`tierIntervalDays`，依序檢查、符合就停）：

| 冷淡 | 距上次叫貨 > 6 個月 | 56 天 |
| 一般 | 其他 | 35 天 |

從未叫貨的客戶（訂單主檔完全查不到）歸「一般」，不特別處理。

**月均叫貨跟近3個月月化金額都用淨額（2026-10-27 補，寄賣調查後確認）**：`月均 = (總叫貨 − 總退貨) ÷ 合作月數`，近3個月同樣扣掉同期退貨。原因：寄賣店約 7 個月整理一次，賣不掉退回、賣得掉的再下一張「轉進貨」單補貨，兩筆都算進「叫貨」等於把同一批貨算兩次——用自強藥局(C113)實測驗證過：2026-08-31 退貨 $17,450、隔天 2026-09-01 立刻下同額新單，退貨跟訂單主檔是兩張完全獨立的表（退貨單/退貨明細，不是訂單主檔的負數、也不是盤點表），退貨單「店名」欄直接存 Customer_ID，不用再 join 到明細。全部134家客戶只有37家有退貨紀錄，其餘97家淨額＝原始叫貨，不受影響。改完 C113 月均從 $3,720 降到 $1,847，P70 從 1,920 降到 1,847，中位數從 1,386 降到 1,263。

**退貨淨額沒有另一個欄位可用**：新客戶資料表 U 欄「一年內累計實收」查過 AppSheet 定義，是純手動輸入的 Price 欄位，沒有公式、沒有 Initial Value，從來沒有人填過——不是壞掉的自動化，就是從沒被使用的空欄位，所以沒有改用「實收」，改用「叫貨−退貨」淨額（兩張來源表都在持續記錄，不需要新增人工輸入流程）。

**排序**：

```
最後接觸日 = max(最後拜訪日, 最後叫貨日)       ← 拜訪跟叫貨取比較近的那個，不是只看拜訪
倍數 = 距最後接觸天數 ÷ 該級建議間隔
從未拜訪也從未叫貨的店：倍數固定 1.0（不特別排最前，也不墊底——沒有任何互動歷史，中性處理）

倍數 ≥ 1（該去了）的店：排在倍數 < 1（還沒到）的店前面
組內排序分 = 倍數 × 月均叫貨，再乘上待追蹤倍率（見下）

冷淡級倍數封頂 2.0（`planner-config.js` 的 `tierRatioCap.冷淡`，2026-10-27 補）：冷淡的店很久沒接觸，
天數一直往上加會讓倍數衝很高（例如良方 378/56=6.75倍），排到前段壓過正在穩定叫貨的店——
冷淡的店偶爾出現就好，排中段即可。只有冷淡設上限，大咖/潛力新店/一般不設上限。
reason 裡會顯示原始倍數跟「封頂算 X」，不會隱藏真實天數。

新店開發（藥局每日異動追蹤篩選分頁）：完全沿用 4.2 公式，不受這次改版影響
```

**待追蹤對排序的影響**（取代第一版的加分制，門檻在 `planner-config.js` 的 `followupMultiplier`）：
- 到期日 ≤ 規劃日：整筆移到 `/api/plan` 回傳的 `anchors`（來源標「待追蹤」），**不參加排名**——等同直接變成「今天一定要去」的錨點候選。
- 還沒到期（含「下次經過」這種沒有具體日期的）：排序分 **乘上** `followupMultiplier`（目前 1.3），不是加法。
- 新店開發那邊不受影響，繼續用 4.2 的 `scoreFollowups` 加分制。

**三種提醒**（顯示在推薦理由，**不寫入待追蹤表**；「首批後沒回購」是分級判斷的一部分，跟「叫貨下滑/叫貨回溫」這組動量指標是分開邏輯，不會同時出現在同一家店上；門檻在 `planner-config.js` 的 `alertThresholds`）：

| 提醒 | 條件 |
|---|---|
| 首批後沒回購 | 合作 ≤ 6 個月、叫貨次數剛好 1 次、距那次 > 60 天（同時決定分級，見上表） |
| 叫貨下滑 | 月均叫貨 ≥ 全體中位數，且近 3 個月月化金額 < 月均 × 30%；**冷淡級的店不標這個**（已經是冷淡了，標下滑沒有新資訊） |
| 叫貨回溫 | 近 3 個月月化金額 > 月均 × 200% |
| 寄賣整理（2026-10-27 第二版，分兩種客人） | 有合約（見下）：寄賣中(資料夾)總額 ≥ 切口金額 × `consignmentReconcileMultiplier`（1.4）→「該對帳：寄賣中 $X / 切口 $Y」。沒合約：維持看天數，訂單「紅單實體狀態」＝寄賣中(資料夾) 且訂單日期距今 ≥ `consignmentCleanupMonths`（7個月）的那些訂單彙整成一行「寄賣N張待整理，最久M個月，共$X」。**兩種都限定在排除規則篩過的名單內**（2026-10-27 修正：第一版掃全部客戶，誤把死客戶 C015/C038 列進來）。**不進 `anchors`、不參加排名以外的位置**——直接顯示在該店自己的推薦理由裡，且沒合約那組的排序分會乘上 `consignmentMultiplier`（1.5），有合約那組目前不調整排序分，只顯示提醒文字 |

**合約資料來源（2026-10-27 新增）**：獨立試算表「客戶合約」（`env.SHEET_CONTRACT` = `10zWisKoSqiMS1v6hwzy4lzIs4CkkCBhuhetN7_jlsbU`，分頁「客戶合約」，欄位：合約ID、Customer_ID、合約起始日、切口金額、合約狀態；另有分頁「客戶合約折扣級距」目前沒用到）。**這份表目前沒開「知道連結的人可檢視」**，gviz 讀回來是 Google 登入頁不是 JSON——`handlePlannerPlan` 用 `.catch()` 吞掉這個錯誤，讀不到就當作沒有任何合約資料（全部店都走沒合約的 7 個月規則），不會讓整個 `/api/plan` 掛掉。**要讓合約資料真正生效，需要把這份表的分享設定改成跟其他 SHEET_* 來源一樣「知道連結的人可檢視」**，使用者自己手動改，不是 Claude 代操作。目前表裡只有 1 筆（C064 成家健保，切口 $50,000），其他簽約店使用者會自己陸續補進去。

## 7. 手機版（之後另外設計，現在先遵守）

手機外勤模式會在電腦版完成後另外設計。現在做電腦版時遵守以下原則，避免之後要重寫：

1. **資料邏輯和畫面分開**：評分、篩選、規則判定、路線排序都寫在 Worker 或獨立的 JS 模組，不要寫在頁面的 DOM 操作裡。手機版會呼叫同一組 API。
2. **API 回傳完整的判定結果**：例如推薦清單直接回傳 `score`、`ratio`、`reason`、`ruleStatus`，前端只負責顯示。
3. **當天路線存在後端**（不是只在瀏覽器）：電腦按「確定」後，手機打開就能拿到同一份路線。
4. **版面不要在 768px 以下破掉**：電腦版的三欄在窄螢幕可以先直接堆疊，不用特別美化，但不能水平捲動或重疊。
5. 先預留手機版會用到的動作：到店、離店、語音紀錄、跳過這站、打給藥師、結案待追蹤。
